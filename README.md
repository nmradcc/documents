# Documents

## NMRA Standards and Conformance Document Development
The NMRA Standards and Conformance department maintains documents for standards, recommended practices, and other purposes for furthering the hobby of model railroading. For a description of NMRA document types, please review [TR-1-2020 S & C Documents and Formatting](https://www.nmra.org/sites/default/files/standards/sandrp/General/TR/tr-1-2020_s_c_documents_and_formating.pdf). When creating a new S & C document, or making a significant refactor of an existing document, please use the template found [here](https://www.nmra.org/sites/default/files/standards/sandrp/General/TR/tr-1-2020.dotx).

Revision history of S & C documents is managed on an NMRA provided Google Drive. To receive a copy of the latest version of an S & C document for editing, please contact the NMRA Tech Chair (Tech-chair@nmra.org) and/or the NMRA Conformance and Inspection Manager (CIManager@nmra.org).

## Issues Tracking
The primary purpose of this repository is to track issues related to NNRA S & C documents. If the issue is not found in this repository, it is likely unknown to the NMRA, and even more likely not to be resolved in the future. [Issues Main Page](https://github.com/nmradcc/documents/issues).

### Filing a new issue
Before filing a new issue, it is a good idea to search the existing open issues to see if it has already been filed. If an existing open issue is a close match, it may be better to add additional commentary to the existing issue rather than file a completely new one.

When creating a new issue, by convention, the title should take the following form:

    <NMRA Document Number> <Short Descritption>

For example:

    S-9.2.1 Decoder Control Bit Definition Confusing

The description field should provide a detailed explanation of the issue, including any supporting material. If the issue references an existing NMRA document, provide as much context as possible (document name, version/date, line number, etc.).

A Label should also be applied to the issue which matches the document number. In the example above, the label should be **9.2.1**.

### Commenting on an Existing Issue
Commenting on existing issues is encouraged. Commentary can include additional information, conversation on what the resolution should be, disagreement about the issue, etc. The intent is to capture a conversation that eventually leads to the best resolution. Having the context for historical archival purposes may also be useful in the future.

### Closing an Issue
The most common way that an issue may be closed is when a resolution has made its way into an approved revision of the relevant document(s).

Issues may also be closed if later analysis determines that the issue does not need resolving. This might be common in the case of a misunderstanding which is resolved by further conversation.

Whenever closing an issue, be sure to comment on why the issue is being closed. This typically takes the form of a reference to the document version that deploys the resolution. If an issue is closed without resolution, be sure to also add the "wontfix" tag to it.

### Issues Tracker Tips
The issues tracker web interface is easy to use and quite powerful. The search capability in particular is quite useful. For example, it is possible to search on labels.

It is a good idea for any document editor to filter issues by the document number label of the document that is currently open for editing. In this way, relevant issues might be resolved at a convenient time.
